# Database migrations

Schema changes outlive the code that made them. Make them reversible in practice, safe on a live database, and tested against the task's own database.

## Workflow

1. Find the migration tool and its folder (`prisma/migrations`, `drizzle/`, `migrations/`, `db/migrate/`). Follow the existing naming and style exactly.
2. Change the schema source (e.g. `schema.prisma`) and **generate** the migration with the project's command (`prisma migrate dev --name <change>`, `drizzle-kit generate`, …). Do not hand-write what the tool generates; review the generated SQL.
3. Never edit a migration that has already been merged to the base branch. Add a new one.
4. Apply it to the task's database (`DATABASE_URL` is set in your shell by Nightshift; use the `database` tool to reset and reseed if needed) and run the tests.
5. Update seed data and fixtures so a fresh database still seeds without errors.

## Safe changes on a live database

- **Adding a column**: make it nullable or give it a default. Backfill in a separate step if needed, then add `NOT NULL` in a later migration.
- **Renaming**: add the new column, write to both, backfill, switch reads, then drop the old one later. A plain rename breaks the running version of the app during deploy.
- **Dropping**: only after the code no longer reads the column. Call it out in the summary.
- **Indexes** on large tables: use `CREATE INDEX CONCURRENTLY` (Postgres) in its own migration when the tool allows it.
- **Enums**: adding a value is fine; removing or renaming needs a migration plan.
- **Data backfills**: batch them, make them idempotent, and keep them out of the request path.

## Checklist before you finish

- Migration generated by the tool, reviewed, and applied cleanly to a fresh database (`database` tool → reset).
- Generated client/types regenerated (`prisma generate`, etc.).
- Seed and tests pass.
- Summary lists the schema change, whether it is backward compatible with the currently deployed code, and any manual step needed on deploy.
